## 二、需求全维度拆解（P0必做 → P1加分 → P2挑战）

### 2.1 P0 必做功能（7大模块）

#### 模块1：多格式教材加载与解析
- **支持格式**：PDF（必做）、Markdown（必做）、TXT（必做）、Word .docx（加分）、Excel（加分）
- **核心要求**：
  - 前端拖拽上传 + 点选上传，支持批量上传多文件
  - 上传后显示文件列表（文件名、格式、大小、处理状态：完成/处理中/失败）
  - PDF解析需处理：章节标题识别（字体大小/粗体/模式匹配）、页眉页脚过滤、图片/表格识别与跳过
  - 统一输出结构化JSON（每个文件一次性完整加载进内存）
  - **数据结构**：`textbook_id, filename, title, total_pages, total_chars, chapters[{chapter_id, title, page_start, page_end, content, char_count}]`

#### 模块2：单教材知识图谱构建与可视化
- LLM提取每章核心知识点（概念、定理、公式、关键事件等）
- 知识点结构化输出：`id, name, definition, category, chapter, page`
- 知识点间关系识别（≥4种类型）：
  | 关系类型 | 说明 | 示例 |
  |----------|------|------|
  | prerequisite（前置依赖） | 学习B前必须掌握A | 动作电位 → 神经递质释放 |
  | parallel（并列关系） | 同一层级的平行概念 | 有丝分裂 ∥ 减数分裂 |
  | contains（包含关系） | 上位概念包含下位概念 | 神经系统 ⊃ 神经元 |
  | applies_to（应用关系） | 某知识应用于另一领域 | 渗透压 → 肾脏功能 |
- **LLM调用约束**：每次调用只处理一个章节，控制上下文长度，Few-shot Prompt + JSON格式约束
- **可视化要求**：前端交互式知识图谱，节点可点击展开详细信息（名称、定义、所属章节、原文段落）

#### 模块3：知识图谱交互
- 节点点击展开详情面板
- 频次可视化：多教材加载后，节点大小/颜色反映知识点在多教材中的出现频次
- 教材来源区分：不同教材来源的知识点用不同颜色标识
- 画布操作：缩放、平移、拖拽移动节点
- 搜索功能：模糊搜索知识点，高亮匹配节点
- 推荐可视化库：D3.js / ECharts / Cytoscape.js / AntV G6（任选）

#### 模块4：跨教材知识图谱融合（核心难点）
这是比赛的核心挑战，涉及去重合并逻辑：
- **语义对齐**：识别不同教材中描述同一事物的知识点（如 "红细胞" = "erythrocyte" = "RBC"）
- **去重算法**（至少实现一种）：
  - 文本Embedding + 余弦相似度（设定阈值判断）
  - LLM直接判断两个知识点是否等价（标准更准确但成本高）
  - 双路结合（推荐方案）
- **融合决策数据结构**：
  - `decision_id` / `action`（merge/keep/remove）/ `affected_nodes` / `result_node` / `reason` / `confidence`
- **压缩率控制**：融合后知识点数量 ≤ 原始总量的70%（即压缩率≥30%）
- **可视化对比**（加分项）：展示融合前后知识图谱的对比变化

#### 模块5：RAG标准问答
- **完整Pipeline**：
  1. **文档分块（Chunking）**：每块500-800字，块间50-100字overlap（sliding window），保留元数据（教材名、章节标题、起始页码）
  2. **向量嵌入（Embedding）**：推荐 sentence-transformers（免费本地）/ OpenAI Embedding API / paraphrase-multilingual-MiniLM-L12-v2 / BGE-small-zh
  3. **向量存储与检索**：FAISS / ChromaDB，用户问题转向量 → 检索 top-5 相关chunk
  4. **混合检索（加分）**：向量检索 + BM25关键词检索 → Rerank重排序
  5. **LLM生成回答**：top-5 chunk作为上下文注入Prompt，约束：仅基于提供的上下文回答 + 逐条标注来源 + 无法回答时明确告知

- **前端交互要求**：
  - 问答输入框，流式展示回答
  - 每条回答附带来源列表（教材名、章节、页码、相关度分数）
  - 每条来源可点击展开查看原始chunk内容
  - 状态提示：正在检索 X 本教材、X 个知识块
- **API接口参考**：
  - `POST /api/rag/index` — 触发教材索引构建
  - `POST /api/rag/query` — 提交问题，返回结构化回答
  - `GET /api/rag/status` — 查询索引状态

#### 模块6：Agent架构说明文档
- 位置：`docs/Agent架构说明.md`
- **必须包含**：
  - a) 架构总览：系统有几个Agent/模块，各自职责，Mermaid架构图
  - b) 设计决策论证：为什么选择这种架构？解决什么问题？为什么用多Agent/为什么不用？Prompt复杂度分析
  - c) 关键流程与接口：上传教材→构建图谱→融合→问答，各Agent间数据如何流转
  - d) 取舍与权衡：发现了哪些备选方案？为什么做这个选择？架构已知局限与改进方向
- **评分逻辑**：不是"用了Agent就高分"，而是对架构设计合理性的论证深度

#### 模块7：Web应用界面
- **SPA单页应用**，Tab切换分区：
  - 左侧：教材管理面板（上传、列表、状态）
  - 中间：知识图谱可视化画布（主视觉区）
  - 右侧：信息面板（Tab切换：融合面板 / RAG问答 / 对话调整 / 报告）
- 响应式设计（非强制），1920×1080分辨率基准
- UI框架：React / Vue / 原生HTML+JS（不限）

### 2.2 P1 加分功能（可选实现，额外加分）
- 知识图谱多视图切换（力导向图 / 树状图 / 桑基图 / 时间线）

- 选一个技术改进点深入研究：
  - Agent协作优化
  - RAG性能优化（分块策略对比、混合检索、Rerank）
  - Prompt工程优化
  - 知识图谱对齐算法改进
  - 压缩率优化

- **必须有实验数据支撑**，没有实测数据的纯论述得分有限

## 四、功能分析 — 核心难点与解决方案映射

| 难点 | 难度 | 关键挑战 | 解决思路 |
|------|------|----------|----------|
| PDF章节结构识别 | ⭐⭐⭐ | 不同PDF格式差异大，字体/排版不一致 | PyMuPDF提取字体信息→字号/粗体聚类→标题层级推断 |
| 知识提取质量 | ⭐⭐⭐⭐ | LLM输出的结构化稳定性 | Few-shot Prompt + JSON Schema约束 + 逐章处理控制上下文 |
| 跨教材知识去重 | ⭐⭐⭐⭐⭐ | 同一概念不同表述的语义对齐 | Embedding相似度(粗筛) + LLM精判(高分裁定) 两阶段流水线 |
| 知识图谱可视化 | ⭐⭐⭐ | 大规模节点的渲染性能 | Canvas/SVG混合渲染，节点数>200时使用WebGL加速 |
| RAG问答准确性 | ⭐⭐⭐⭐ | 检索召回率 + 幻觉抑制 | 混合检索 + Rerank + 严格来源约束Prompt |
| Agent架构设计 | ⭐⭐⭐⭐ | 合理划分Agent边界，避免过度设计 | 按数据流划分：解析→提取→融合→检索→生成，Agent间通过结构化数据通信 |

## 五、产品设计方案

### 5.1 用户角色
- **主要用户**：学科教师/教学管理者
- **核心场景**：教师想了解多本教材对同一学科的覆盖情况，快速定位知识点交叉与缺失

### 5.2 用户旅程
1. **上传阶段**：用户拖拽/选择7本PDF教材 → 前端显示上传进度 → 后端异步解析 → 前端实时更新解析状态
2. **图谱生成**：解析完成后自动触发知识提取 → 每本教材生成独立知识图谱 → 前端可视化展示
3. **融合阶段**：用户触发"融合分析" → 系统自动识别重复知识点 → 生成融合建议列表 → 用户查看决策详情
4. **人工调整**：教师通过自然语言对话调整融合结果（"我觉得XX和YY应该分开"）→ 系统实时更新图谱
5. **问答阶段**：教师通过RAG问答获取教材内容答案 → 每条回答带来源引用
6. **报告导出**：查看融合报告摘要 → 下载完整报告

### 5.3 界面布局

## 六、技术路线选择

### 6.1 推荐技术栈（综合考虑开发效率与评分最大化）

| 层级 | 技术选型 | 选型理由 |
|------|----------|----------|
| **后端框架** | FastAPI (Python) | 异步支持好、自动生成API文档、生态成熟、评委推荐 |
| **前端框架** | React 18 + TypeScript | 生态最大、组件库丰富、SPA支持好 |
| **知识图谱可视化** | Cytoscape.js | 专为图数据设计，交互API完善，支持拖拽/缩放/布局算法 |
| **大模型API** | DeepSeek API | 性价比最优，中文能力强，支持结构化输出 |
| **Embedding模型** | BGE-small-zh / sentence-transformers | 中文语义匹配效果好，可本地运行 |
| **向量数据库** | ChromaDB | 轻量级、Python原生、零配置、适合5小时快速搭建 |
| **Agent框架** | LangGraph | 状态图模型清晰，适合多步骤流程编排，有Mermaid导出 |
| **PDF解析** | PyMuPDF (fitz) + pdfplumber | 提取文本+字体信息+表格，互补使用 |
| **部署平台** | 魔搭创空间 (免费GPU) | 赛事推荐，免费额度，国内可访问 |

### 6.2 备选方案对比

| 场景 | 推荐方案 | 备选方案 | 切换条件 |
|------|----------|----------|----------|
| 可视化库 | Cytoscape.js | ECharts/AntV G6 | 如需更丰富图表类型用ECharts |
| 向量库 | ChromaDB | FAISS | 数据量极大(>10万chunk)时用FAISS |
| LLM API | DeepSeek | 通义千问/OpenAI | 按可用性和价格切换 |
| 前端 | React | Vue 3 | 团队熟悉度优先 |

### 6.3 5小时时间分配建议

| 时间段 | 任务 | 产出 |
|--------|------|------|
| 前30分钟 | 项目脚手架搭建，前后端联通 | GitHub仓库、Hello World可运行 |
| 第1-3小时 | P0功能敏捷实现：文件解析 → 知识提取 → 图谱可视化 → 融合算法 → RAG | 核心功能可演示 |
| 第3-4小时 | 写文档：Agent架构说明 → 需求分析 → 系统设计 → 融合报告 → README | 文档体系完整 |
| 第4-4.5小时 | 部署上线，确保在线URL可访问 | 可公开访问的演示地址 |
| 最后30分钟 | 检查提交完整性，补缺补漏，P2论文（如有余力） | 最终提交就绪 |

### 6.4 数据流架构

```
用户上传教材 → 文件解析模块 → 结构化章节JSON
                            ↓
              LLM知识提取模块 → 知识点JSON + 关系JSON
                            ↓
              图谱构建模块 → 单教材知识图谱
                            ↓
              融合引擎(Embedding+LLM) → 融合决策列表
                            ↓
              人工对话调整 → 最终融合图谱
                            ↓
        ┌───────────────────┼───────────────┐
        ↓                   ↓               ↓
   RAG索引构建       前端可视化渲染      融合报告生成
        ↓
   RAG问答服务 → 用户提问 → 检索+生成 → 来源标注回答
```

## 七、风险点与应对策略

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 7本教材826MB太大，加载慢 | 高 | 体验差 | 异步解析+进度反馈+分教材并行处理 |
| LLM API限流/不稳定 | 中 | 阻塞提取流程 | 本地缓存中间结果 + 重试机制 + 批量调用控制 |
| 知识去重准确率低 | 高 | 评分受限 | 双路策略：Embedding粗筛+LLM精判，提供人工修正入口 |
| 前端大图渲染卡顿 | 中 | 体验差 | 限制默认展示节点数 + 虚拟化渲染 + Web Worker |
| 时间不足 | 高 | 完赛风险 | 严格按MVP优先级，P0不可少，P1选择性做 |
